3. Project purpose, research contribution, and success definition
3.1 Problem statement
Small offline language models have limited capacity for factual memorization and become stale when knowledge changes. Conventional domain fine-tuning can inject knowledge but couples facts to model weights, complicates updates, obscures provenance, and does not naturally support installing or removing independent domains. PackRAG-MoR separates the reasoning/generation model from mutable specialist knowledge.
3.2 Core research question
Can an ultra-small adaptive-compute language model become a useful offline specialist when factual memory, versioning, provenance, and retrieval structure are moved into independently installable signed Knowledge Packs?
3.3 Secondary research questions
• How much does hybrid sparse+dense retrieval improve a small MoR compared with sparse-only or dense-only retrieval?
• Does a lightweight structural relation layer improve multi-hop retrieval without the complexity of a full graph-RAG system?
• Given the same evidence, does MoR behave differently from the authors’ Vanilla and Recursive 360M baselines on grounding, distractors, citations, and latency?
• When specialist knowledge is static and small, how does PackRAG compare with parametric/domain adaptation? This is an evaluation baseline, not a reason to merge knowledge into the primary model.
3.4 What the capstone claims
• A reusable architecture for verifiable, signed, offline, downloadable external knowledge modules for a tiny adaptive-compute generator.
• An Android-native hybrid retrieval runtime that does not require a server, Python, a vector database service, or network connectivity.
• A rigorous experiment isolating retrieval architecture, generator architecture, citations, abstention, stale/conflicting evidence, and pack install/remove/update behavior.
3.5 What the capstone does not claim
• It does not claim that MoR or PackRAG is generally equivalent to a 7B model.
• It does not claim that signatures prove source truth; signatures prove publisher identity and payload integrity only.
• It does not claim universal multilingual generation quality. English is the generator-language baseline; packs may store multilingual authoritative sources and verified generator-language renderings.
• It does not claim that RAG always beats parametric specialization. A parametric/domain-adaptation baseline is explicitly allowed for comparison.
• The install/remove demonstration proves application access to pack evidence, not erasure of facts that may already exist in model weights.
• A syntactically valid citation proves linkage to a supplied source ID, not semantic entailment. Claim support is an empirical evaluation metric, not a parser guarantee.
4. Scope and non-goals
4.1 Mandatory scope
• Official pretrained 360M MoR integrated on desktop and targeted on Android.
• KPack v1 builder, validator, signer, inspector, and deterministic archive output.
• Two real signed packs in distinct domains: a bounded Morocco Labour Code demonstrator and a technical repair/maintenance demonstrator.
• Android pack import, verification, install, removal, update, rollback warning, and source inspection.
• Hybrid FTS5 BM25 + exact dense retrieval + RRF fusion + metadata validity filtering.
• Graph-Lite relation schema plus a disabled-by-default one-hop experimental retrieval profile for ablation.
• Evidence prompt, structured citation IDs, post-generation citation validation, and abstention.
• Pack/no-pack/update/corruption demo fully offline.
• Benchmark and ablation harness with reproducible result files.
• A validated standard tiny instruction-model Android fallback MUST be available by the end of Week 1; it is a product-continuity backend, not a replacement for MoR research.
• English is the only guaranteed end-to-end question/answer language in v1.2. Arabic/French canonical sources and multilingual retrieval remain supported research inputs.
4.2 Explicit non-goals for v1
• No cloud inference or server-side retrieval.
• No full MiniRAG, LightRAG, Qdrant, Milvus, Neo4j, or other service database on Android.
• No HNSW/IVF/PQ unless an actual pack exceeds the exact-scan budget and profiling proves a need.
• No voice, camera, maps, Bluetooth mesh, or agentic tool execution.
• No pack-contained scripts, plugins, native libraries, adapters, LoRA weights, prompt templates that override app policy, or executable code.
• No neural query rewriting or cross-encoder reranker in the MVP.
• No neural KV-cache Knowledge Packs in KPack 1.0.
• No retrieval-aware MoR router modification on the critical path.
• No requirement to train MoR from random initialization.
• No public model-weight redistribution until the checkpoint licensing status is verified separately from the repository license.
5. System requirements
5.1 Functional requirements
FR-01: The app MUST answer using only evidence returned from active verified packs when PackRAG mode is enabled.
FR-02: The user MUST be able to install and remove packs without changing generator weights.
FR-03: A pack MUST remain usable without Internet access after installation.
FR-04: Every displayed pack-derived answer MUST expose at least one valid source citation or be rejected as ungrounded.
FR-05: The app MUST support a no-answer state and render it as insufficient evidence, not as an invented answer.
FR-06: The app MUST support multiple installed packs and explicit user activation/deactivation.
FR-07: The app MUST preserve source provenance and exact locators such as article, section, and page when available.
FR-08: The app MUST support source validity intervals and an optional query as-of date.
FR-09: The app MUST reject packs whose signature, payload hashes, schema, dense-index contract, or SQLite integrity check fails.
FR-10: The app MUST permit a verified replacement version to be installed atomically without mutating the active pack in place.
FR-11: The same KPack content MUST be queryable by the desktop reference runtime and Android runtime.
FR-12: The app MUST remain functional in airplane mode; the release/demo flavor MUST omit Android INTERNET permission.
5.2 Non-functional requirements
NFR-01: All pack and retrieval data formats MUST be deterministic and versioned.
NFR-02: The generator backend MUST be replaceable behind a stable interface.
NFR-03: The pack format MUST be independent of a particular vector-search engine.
NFR-04: The Android retrieval runtime SHOULD complete query embedding + retrieval within 500 ms on a modern flagship and within 1,000 ms on a recent midrange device for packs within the v1 size envelope.
NFR-05: Pack retrieval SHOULD use no more than four evidence chunks and 1,200 generator tokens by default.
NFR-06: All benchmark inputs, pack revisions, model hashes, and runtime versions MUST be recorded in result manifests.
NFR-07: The system MUST fail closed on verification/security errors and fail gracefully on retrieval/model errors.

7. Generator model and model policy
FROZEN DECISION — The primary generator is the authors’ official pretrained 360M expert-choice MoR checkpoint; from-scratch training is not a dependency for project completion.
7.1 Why this checkpoint
The official repository publishes pretrained 360M Vanilla, Recursive, and MoR checkpoints and an expert-choice routing analysis notebook. Using the released model removes uncertainty about base-language pretraining and makes the capstone’s research contribution the modular memory system rather than reproduction of a published base checkpoint.
7.2 Generator runtime contract
interface GeneratorBackend {
    fun load(modelPath: String): ModelInfo
    fun generate(
        prompt: String,
        maxNewTokens: Int = 256,
        temperature: Float = 0.0,
        topP: Float = 1.0,
        stopStrings: List<String>
    ): GenerationResult
    fun close()
}

GenerationResult:
- text
- promptTokens
- generatedTokens
- timeToFirstTokenMs
- totalLatencyMs
- averageTokensPerSecond
- modelHash
- backendName
- quantization
7.3 Immediate generator Gate G0
FROZEN DECISION — Before substantial PackRAG implementation, the released MoR checkpoint MUST run the 25-question gold-evidence Gate G0. G0 has three outcomes: PASS, PARTIAL, or FAIL. PARTIAL triggers a small evidence-use SFT pilot; clear FAIL keeps MoR as the desktop research generator and moves the product path to the validated instruction-tuned fallback.
G0 bypasses retrieval and supplies perfect evidence. PASS requires all category thresholds below. PARTIAL means the model remains coherent and evidence-sensitive but misses one or more PASS thresholds while meeting at least: direct answer 5/10, citation compliance 3/5, abstention 2/5, and distractor resistance 2/5. FAIL means it falls below the PARTIAL floor in two or more categories, repeatedly ignores the evidence-only instruction, or produces unusable output. PASS proceeds without SFT; PARTIAL starts the 500–2,000-example pilot; FAIL does not justify a large adaptation run. After a pilot, run a separate 50-question gold-evidence gate before deciding whether to scale training.
7.4 Dynamic context budget
fixed_prompt_tokens = tokenize(system + context metadata + question + source wrappers)
available_evidence = max(0, 1536 - fixed_prompt_tokens)
actual_evidence_budget = min(1200, available_evidence)

prompt_tokens = tokenize(final_prompt)
max_new_tokens = min(512, 2048 - prompt_tokens)

If actual_evidence_budget <= 0 or max_new_tokens <= 0:
    do not truncate policy/question silently; return INPUT_TOO_LONG and ask for a shorter query.
All budgeting MUST use the exact tokenizer paired with the official MoR checkpoint. Evidence selection operates on tokenized canonical/generator text plus wrapper overhead, not character counts or approximate word counts.
7.5 Quantization sequence
1. Validate FP32/BF16 desktop generation against the official implementation.
2. Export an unquantized or FP16 Android correctness model.
3. Introduce INT8 quantization and compare token-level/logit sanity plus benchmark outputs.
4. Only after correctness and latency are stable, evaluate INT4/mixed quantization as an optimization experiment.
If INT8 export or a custom MoR operation is unstable, FP16 is the correctness fallback. The capstone does not fail because INT4 is unavailable.
7.6 Checkpoint redistribution policy
The repository is Apache-2.0, but the public checkpoint files do not currently carry a separately verified weight license in this specification. Therefore the public project repository MUST exclude the model weights and provide a download/setup script pointing to the authors’ release. The private capstone demo build MAY bundle the downloaded checkpoint. Public redistribution of the weights is deferred until license confirmation.
7.7 Required MoR runtime measurements
• Prefill latency and average recursion depth/selected-token fraction.
• Decode latency in ms/token and tokens/s.
• Decode average recursion depth/selected-token fraction for generated tokens.
• Peak RAM and model/state memory.
• The thesis MUST NOT claim autoregressive decode speedup from adaptive routing unless these measurements demonstrate it.
7.8 Product-continuity Android fallback
FROZEN DECISION — HuggingFaceTB/SmolLM2-360M-Instruct is the named v1.2 product fallback because it is a standard 360M-class instruction-tuned Llama architecture with an Apache-2.0 model release. It MUST be tested on the target phone in Week 1 using the same gold-evidence prompt contract. The preferred Android implementation is llama.cpp/GGUF behind GeneratorBackend. If a different standard backend is substituted, an ADR and the same golden tests are required.
The fallback does not replace MoR in the research question. MoR remains the primary desktop research generator and the Android target while viable. For fair PackRAG comparisons, the fallback uses the same evidence selection, English question policy, prompt budget, deterministic decoding, and evaluation set.
8. KPack 1.0 package specification
FROZEN DECISION — A Knowledge Pack is immutable data. It contains no executable code, model adapters, scripts, native libraries, or behavior overrides.
8.1 Archive layout
<pack-id>-<version>.kpack   # ZIP transport container
├── manifest.json             # RFC 8785 canonical JSON bytes
├── manifest.sig              # raw 64-byte Ed25519 signature
├── knowledge.sqlite          # immutable evidence/provenance/FTS/relations DB
├── dense.kdx                 # KDX1 normalized float32 dense matrix
└── sources/                  # OPTIONAL redistributable authoritative snapshots
    └── ...
No neural/ directory exists in KPack 1.0. Future schema versions may add extensions, but v1 parsers MUST reject unknown executable-like entries and MUST ignore no payload that is not declared in the signed manifest.
8.2 Archive safety and logical reproducibility
• UTF-8 normalized forward-slash paths only.
• Entries sorted lexicographically by path.
• No absolute paths, drive prefixes, “..” segments, symlinks, hardlinks, devices, or duplicate paths.
• Compression method: DEFLATE for text/SQLite; STORED is allowed for already-compressed source snapshots.
• ZIP entry timestamp normalized to 1980-01-01 00:00:00 for transport stability; semantic release_timestamp lives in manifest.json.
• Maximum 5,000 entries, 512 MiB total uncompressed size, and 256 MiB per entry in v1.
• Every payload entry other than the two control files manifest.json and manifest.sig MUST appear exactly once in manifest.files with byte length and SHA-256. manifest.json MUST NOT list or hash itself; manifest.sig is verified separately.
• Byte-identical ZIP output across different ZIP/zlib implementations is NOT a v1 requirement. Logical content identity is SHA-256(manifest.json exact canonical bytes); archive_transport_sha256 is recorded separately for the produced .kpack file.
8.3 Manifest schema
8.4 Signature rule
The builder serializes manifest.json using RFC 8785 JSON Canonicalization Scheme, writes those exact bytes to the archive, and signs those exact bytes with Ed25519. The Android verifier MUST NOT semantically trust or reserialize the manifest before signature verification. Because key_id is inside the signed JSON, the release trust store is intentionally small: the verifier tries the raw 64-byte signature against each pinned release public key (maximum eight keys in KPack 1.0), requires exactly one key to verify, then parses manifest.json and requires publisher.key_id to match that verified key. Only after this step may schema, compatibility, paths, counts, or calibration fields be accepted.
8.5 Trust model
• Release/demo app contains a built-in trust store of approved publisher public keys keyed by key_id.
• Signature verification selects the signer cryptographically by trying the bounded pinned-key set; unverified JSON is never trusted for key selection.
• Private signing keys never exist on the phone.
• A valid signature proves integrity and publisher-key possession; it does not prove factual correctness.
• Release v1 does not allow arbitrary third-party publisher keys to be silently trusted. A future “advanced trust” UI can be added as a separate feature.
• Debug builds may use a dedicated test key whose key_id cannot be confused with the release key.
8.6 Android Ed25519 implementation
FROZEN DECISION — Android minSdk 26 MUST NOT rely on platform java.security.Signature for Ed25519. The v1 verifier uses com.google.crypto.tink:tink-android:1.23.0 with RAW Ed25519 signatures and a pinned release public key.
• manifest.sig is a standard 64-byte Ed25519 signature over the exact raw manifest.json bytes.
• The PC builder uses a compatible Ed25519 implementation and stores the public key/key_id in release metadata; the private key never ships.
• A fixed cross-language test vector is mandatory: PC signs the canonical manifest bytes; Android Tink verifies the exact signature; wrong-message and wrong-key tests must fail.
• The trust store is application-owned. Packs cannot add trusted keys.
8.7 Runtime-policy ownership
• KPack is data-only. It MAY carry calibration values and compatibility identifiers, but it MUST NOT redefine mobile-v1 candidate counts, RRF k, graph limits, evidence chunk/token caps, query rewrite policy, reranker policy, or memory/CPU limits.
• The application owns the frozen mobile-v1 profile and clamps all pack-provided numeric calibration values to schema-defined finite ranges.
• Release KPack v1.2 supports one active dense embedding profile only. A pack with a different profile can be inspected but cannot be activated for retrieval.

9.6 Canonical text versus retrieval/derived text
canonical_text is the source-faithful evidence used for citation display. search_text may be normalized, prefixed with headings/identifiers, and language-normalized for retrieval. Any generator-language translation or other derived rendering is stored separately with provenance; it never replaces canonical_text. Citations always resolve back to canonical_text and the source record.
9.7 Derived text / translation provenance
CREATE TABLE derived_texts (

  language TEXT NOT NULL,
  text TEXT NOT NULL,
  text_sha256 TEXT NOT NULL,
  derivation_method TEXT NOT NULL,  -- official_translation, human_reviewed_translation, machine_draft

);
For high-stakes release packs, generator-language derived text MUST be official_translation or human_reviewed_translation. Machine-only drafts MAY exist in builder workspaces but MUST NOT be used as release evidence text. The app records which representation was shown to the generator and always exposes canonical source text to the user.
10. KDX1 dense-vector format
FROZEN DECISION — KDX1 uses normalized little-endian float32 vectors. No HNSW, IVF, PQ, or vector database is used in the v1 mobile runtime.
The chunks.dense_row value maps directly to the row in dense.kdx. A separate dense_ids file is deliberately removed to eliminate an extra synchronization surface. The validator checks that dense_row is a contiguous 0..N-1 permutation, vector_count equals chunk_count, all values are finite, vector norms are within 1±0.01, and actual file size equals exactly 84 + vector_count × dimension × 4 bytes. Trailing or truncated payload bytes are invalid.

11. Embedding subsystem
FROZEN DECISION — Default embedding profile: ibm-granite/granite-embedding-97m-multilingual-r2, pinned to an exact repository revision, 384 dimensions, L2-normalized outputs.
11.1 Why this model
The 2026 Granite 97M multilingual R2 model is explicitly intended for latency-sensitive and edge retrieval, supports 200+ languages with enhanced Arabic and French support, uses 384-dimensional embeddings, and is Apache-2.0. KPack v1 freezes this as the only active dense profile to avoid multi-embedder runtime complexity. Darija and Arabizi performance are not assumed from Arabic support and are tested explicitly.
11.2 Runtime policy
• Document/chunk embeddings are computed only during PC pack construction.
• Android computes one query embedding per user query.
• The embedding model is app-level and shared by all packs; packs never duplicate embedder weights.
• Android embedder backend is ONNX Runtime Mobile CPU for v1. Hardware acceleration may be evaluated later but is not required.
• The pack pins model id, exact revision, tokenizer assets hash/model hash, pooling behavior, dimension, normalization, and maximum embedding input length.
• KPack v1 release packs MUST use embedding_profile_id=granite97m-multi-r2-384-v1. An incompatible pack may be inspected but MUST NOT be activated for search; sparse-only activation is not supported in v1.
• Before the first Moroccan-law release, run a 24-query retrieval-only language-form probe: 6 Darija Arabic-script, 6 Arabizi, 6 French, and 6 English paraphrases mapped to verified gold chunks. Report Recall@4 by language form. This does not authorize multilingual generation. If Granite retrieval is clearly inadequate in either Darija form, open an ADR and benchmark multilingual-E5-small before release.
11.3 Input construction
embedding_text =
  title + "
" +
  section/article identifiers + "
" +
  search-safe contextual prefix + "
" +
  canonical or verified generator-language text

The canonical evidence itself is stored separately and is never overwritten by retrieval normalization.
11.4 Query normalization
• Preserve raw user query for display/logging.
• Create search query with Unicode NFKC normalization and whitespace collapse.
• Lowercase where language rules permit; do not destructively lowercase source IDs that are case-sensitive.
• For Arabic search normalization remove tatweel and optionally diacritics in search_text only; canonical text remains unchanged.
• Extract explicit identifiers using deterministic patterns and the aliases table.
• Do not ask MoR to rewrite the query in v1.

12.1 Source acceptance rules
• Every source MUST have publisher, canonical URI when available, retrieval date, language, original SHA-256, source type, and license metadata.
• High-stakes facts MUST prefer primary/authoritative sources over commentary.
• If redistribution_allowed=false, the public pack MUST omit the original snapshot and must comply with the source license for any extracted text. A private research pack may be built only when lawful.
• Scanned/image-only sources MAY be OCRed, but OCR output MUST be sampled against the original and high-stakes numeric/legal content MUST be manually verified.
• Derived translations MUST record their derivation status and reviewer when human reviewed.
12.2 Chunking policy
• Legal text: article/section boundaries take priority over token targets. Do not split a short article merely to hit a fixed size.
• Manual/procedure text: keep procedure step groups, warnings, causes, and remedies structurally connected.
• General prose: target 300–450 generator tokens, hard maximum 500, with overlap only when a semantic boundary would otherwise be lost.
• Every chunk stores a stable locator and parent relationship.
• Chunk IDs are deterministic: SHA-256(source_id + canonical locator + canonical_text_sha256), encoded as a short stable hex identifier with collision checking.
12.3 Calibration requirement
Every official release pack MUST include 40 manually verified development/calibration queries, separate from the final held-out PackBench questions. Calibration estimates query-embedding relevance thresholds on eligible data; RRF is used only for ranking and is never interpreted as a probability of relevance. KPack v1.2 stores min_agreed_dense_cosine and min_dense_only_cosine plus the measured calibration precision/recall and dataset hash. Exact identifier hits are retrieval-priority signals, not automatic permission to answer. A pack without calibration can be installed only in developer mode and is labeled UNCALIBRATED.
13. Runtime retrieval algorithm
13.1 Pack selection
FROZEN DECISION — The user explicitly selects the active pack set. Pack/domain/jurisdiction selection is not delegated to the 360M generator in v1.
The Pack Registry supplies only installed, signature-verified, schema-compatible versions. A query may specify an as_of_date; otherwise the current date is used for validity filtering. For legal packs, the user interface exposes the active jurisdiction and date.
13.2 Frozen application retrieval profile mobile-v1
Ranks are 1-based. Application constants above cannot be changed by a pack. General candidate ordering is deterministic: priority_tier ASC, rrf_score DESC NULLS LAST, exact_identifier_match DESC, dense_score DESC NULLS LAST, pack_id ASC, chunk_id ASC. authority_rank is NOT a global retrieval sort key; it is applied only inside the legal conflict-resolution procedure in Section 14.
13.3 Retrieval candidate tiers and steps
1. Validate product-language policy; v1.2 end-to-end generation accepts English questions. Preserve the raw query, normalize the retrieval query, and extract aliases/identifiers deterministically.
2. For each active pack, compute eligibility before top-k: embedding profile, jurisdiction, source status, and the effective intersection of source + chunk validity intervals. A null chunk boundary inherits the source boundary.
3. Run FTS5/BM25 and return sparse top-24 with 1-based sparse_rank. Resolve explicit aliases/identifiers separately. Eligible exact-identifier hits become priority_tier=0 but do not prove semantic answerability.
4. Compute one query embedding and exact dot product against normalized KDX1 vectors; remove ineligible rows before choosing dense top-24.
5. Compute local per-pack RRF(k=60) for ranking only. RRF candidates are priority_tier=1. Keep at most 16 fused candidates per pack.
6. Graph-Lite is disabled in mobile-v1. The benchmark-only graph profile expands one hop from the top six eligible seeds, adds at most twelve graph-only candidates as tier 2, records seed/relation metadata, and assigns no fabricated RRF score.
7. Merge per-pack candidates, deduplicate by canonical source hash + canonical text hash, preserve pack provenance, and cap the cross-pack pool at 32.
8. Run CandidateRelevanceGateV1. If it fails, return INSUFFICIENT_EVIDENCE before generation.
9. Compute the exact MoR-tokenizer evidence budget, then select the final evidence set (≤4 chunks). Selection is deterministic and redundancy-aware. In the graph experimental profile, a nonredundant linked candidate with relation_type in {exception_to, amends, requires, procedure_next, procedure_previous} MAY replace the lowest-value redundant ordinary candidate; this rule never uses benchmark gold labels.
10. Run FinalEvidenceAdmissionGateV1 on the actual selected evidence. If it fails, return INSUFFICIENT_EVIDENCE. Freeze the evidence set, pack versions, as-of date, and retrieval profile before generation.









13.4 RRF, CandidateRelevanceGateV1, and FinalEvidenceAdmissionGateV1
RRF(c) = Σ 1 / (60 + rank_i), with 1-based ranks for sparse and dense lists containing c. RRF is a deterministic rank-fusion score only; it is NOT a calibrated relevance probability.

CandidateRelevanceGateV1 (after source+chunk eligibility filtering):
1. If there are no candidates: FAIL.
2. An eligible exact identifier hit is marked retrieval_relevant=true, but it grants no automatic permission to answer.
3. For non-identifier candidates, the highest-ranked candidate is marked retrieval_relevant when either:
   a. it occurs in both sparse and dense lists AND dense_score >= pack.calibration.min_agreed_dense_cosine; or
   b. it is dense_rank==1 AND dense_score >= pack.calibration.min_dense_only_cosine.
4. If no candidate is retrieval_relevant: FAIL; otherwise PASS to evidence selection.

FinalEvidenceAdmissionGateV1 runs AFTER token budgeting on the exact evidence that will be sent to the generator. It requires at least one selected retrieval_relevant or eligible exact-identifier chunk and rechecks validity/pack version consistency. It does not claim semantic sufficiency. The generator is still instructed to abstain when the selected passages do not answer the question, and true answerability is measured on held-out tests.
13.5 Graph-Lite enablement rule
The relations schema is always allowed, but runtime graph expansion is disabled by default. Graph-Lite is an exploratory ablation in v1.2, not a mandatory feature. It may be enabled in the final demo only if development-set evidence coverage improves without a material regression in held-out grounded accuracy and median retrieval latency increases by no more than 20%. Because the multi-hop subset is small, v1.2 does not use a fine-grained +3-point activation threshold as if it were statistically precise. Candidate recall and final-evidence source coverage are both reported.
13.6 Cross-pack orchestration
Each pack is searched independently with identical mobile-v1 limits. The orchestrator then merges priority-tier candidates directly; it does not perform a second RRF transform. Duplicates are detected by original source hash + canonical text hash. The final evidence object retains pack_id and pack_version for every chunk.
14. Temporal, jurisdiction, and authority semantics
FROZEN DECISION — “Prefer latest” is not a legal rule. Eligibility is determined by jurisdiction, as-of date, legal status, and publisher-defined authority rank before recency is used as a tie-breaker.
14.1 Source validity algorithm
eligible(source, chunk, query):
  if query.jurisdiction != null and source.jurisdiction != query.jurisdiction: reject
  date = query.as_of_date or current_date
  start = later_non_null(source.effective_from, chunk.effective_from)
  end_excl = earlier_non_null(source.effective_until_excl, chunk.effective_until_excl)
  if start != null and date < start: reject
  if end_excl != null and date >= end_excl: reject
  if source.legal_status in {repealed, superseded} and query explicitly asks current law: reject
  otherwise: keep

Missing chunk boundaries inherit the source interval. Empty source boundaries mean unknown/open at that side and MUST be exposed in provenance rather than silently invented.

Ranking rule: retrieval relevance is primary across unrelated candidates. authority_rank does NOT make an irrelevant legal document outrank a relevant one. Authority is applied when candidates represent the same provision/proposition, are explicitly linked as amendments/supersessions/exceptions, or present a detected conflict; within that conflict set, stronger authority and the as-of validity relation decide which source is preferred. Remaining ties use deterministic retrieval rank, then pack_id and chunk_id.
14.2 Pack freshness
effective_from is an ISO YYYY-MM-DD inclusive boundary. effective_until_excl is an ISO YYYY-MM-DD exclusive boundary. Pack freshness is advisory. A pack can be STALE while sources remain legally/factually valid. The UI always displays the legal query as-of date for law-pack answers and allows the user to change it; device date is merely the default because an offline clock can be wrong. A stale pack is not silently disabled. A cryptographically invalid pack is disabled.

17.1 Rollback policy
Automatic rollback to an older version is forbidden. A deliberate user rollback is permitted from Pack Details and must display an “older content” warning. 17.2 Corruption test
The automated test suite MUST flip one byte in knowledge.sqlite and one byte in dense.kdx and confirm the pack is rejected with a hash mismatch before activation. It MUST also test a traversal filename, duplicate filename, oversized-declared archive, unknown signer, wrong signature, invalid KDX1 magic, and broken SQLite integrity.

19. MoR Android deployment plan
19.1 Days 2–5 export/operator spike and export sequence
1. Load the official expert-choice MoR checkpoint and reproduce desktop generation/evaluation on Days 1–2.
2. Create an inference-only wrapper with batch size 1, explicit cache/state types, and export-friendly gather/scatter behavior.
3. On Days 2–5, attempt torch.export / ExecuTorch lowering and write mor_export_report.json listing delegated, portable, decomposed, unsupported, and custom-op-required operators plus shape/control-flow blockers.
4. Delegate supported linear/attention kernels to XNNPACK. Keep router selection/gather/scatter as portable kernels or custom C++ ops when delegation is impossible.
5. Validate prompt logits or deterministic greedy output against the PyTorch backend on a small golden suite.
6. Profile prefill recursion, decode recursion, TTFT, ms/token, tokens/s, and peak memory separately.
7. By end of Week 3, classify Android MoR as viable / viable-with-custom-ops / research-only and begin the fallback path if necessary; MoR optimization may continue in parallel.
8. Apply INT8 quantization only after correctness; rerun the full golden suite.
9. Only then evaluate Vulkan/vendor acceleration or INT4.
19.2 Inference risk note
The official MoR repository is a research PyTorch implementation and has an inference-time expert-choice routing question/discussion that must be measured rather than treated as a proven limitation. Android deployment remains the highest-risk component. The project records prefill and decode recursion separately and makes no adaptive-decode speed claim without measurement. This risk is isolated behind GeneratorBackend.
19.3 Defined fallback if Android MoR is blocked
If the adaptive MoR backend is still classified research-only at the end-of-Week-3 viability gate, the capstone retains MoR as the primary research generator on desktop. The live Android product demonstration uses the Week-1-validated HuggingFaceTB/SmolLM2-360M-Instruct fallback through its standard Llama-compatible backend. The report MUST label this backend explicitly and MUST NOT imply the Android result is adaptive MoR. The authors’ Recursive 360M checkpoint remains a research architecture control, not the sole product fallback.
20. Evidence-use post-training policy
FROZEN DECISION — Evidence-use SFT is a planned contingency, not a remote stretch. Gate G0 runs immediately; the gold-evidence gates determine whether a small SFT pilot is worthwhile. The project does not commit to multi-billion-token retrieval-native training or a large synthetic corpus before learning curves justify it.
20.1 Gold-evidence gates
Gate G0 is defined in Section 7.3 and runs on Days 2–3. PASS continues without SFT. PARTIAL triggers the pilot below. FAIL moves MoR to research-only unless there is a compelling, measured reason to revisit it. After any pilot, evaluate on a separate 50-question held-out gold-evidence set. Continue adaptation only if grounded-answer correctness, citation support/compliance, and abstention improve jointly; no single formatting metric may hide a regression in answer quality.
20.2 If SFT is triggered
• Use one shared model; no pack-specific adapters.
• Pilot size: 500–2,000 carefully checked examples, checkpointing at approximately 500, 1,000, and 2,000.
• Scale to 5,000, then 10,000, and at most 20,000 examples for the capstone only when held-out grounded score improves by at least 2 absolute points at the previous stage with no material regression in abstention or citation support.
• A larger dataset requires an ADR and must not block the product path.
• Example types: answer-from-evidence, exact citation, no-answer, hard distractor, conflicting/obsolete evidence, wrong jurisdiction, two-source synthesis.
• Prefer full-parameter supervised fine-tuning on the home RTX 4090 Laptop if memory allows; gradient accumulation is acceptable. LoRA is a fallback, not a pack artifact.
• Evaluate every checkpoint on a held-out gold-evidence set. Stop when two successive checkpoints improve the primary grounded score by <1 absolute point.
• Do not use pack benchmark test questions as training examples.

22. Evaluation design: PackBench
22.1 Dataset size and split
Each release pack has 40 manually verified development/calibration queries and 40 completely separate final held-out PackBench queries. A suggested held-out distribution per pack is: 14 direct evidence, 6 exact identifier, 6 paraphrase/semantic, 4 multi-source/multi-hop, 4 no-answer, 3 stale/conflict/version, and 3 adversarial/distractor = 40. An additional 20 system-level tests cover install/remove/update, wrong-pack activation, corruption, and cross-pack retrieval. Mandatory PackBench total = 180 verified cases. G0, the 50-question gold-evidence gate, and the 24-query multilingual retrieval probe are reported separately and are not counted as PackBench. No held-out test question is used in SFT, graph decisions, or threshold calibration.
22.2 Retrieval metrics
• Recall@1, Recall@4, and MRR for gold chunks.
• Evidence sufficiency precision/recall and abstention trigger accuracy.
• Exact identifier retrieval accuracy.
• Multi-hop source coverage: fraction of required gold sources present in final evidence.
• Retrieval latency: embedder, sparse, dense, fusion/filters separately.
22.3 Generation metrics
• Grounded answer correctness: exact match/F1 when applicable plus manually adjudicated correctness for open answers.
• Citation validity: all cited IDs exist in supplied evidence.
• Citation precision: cited evidence actually supports the associated claim.
• Citation recall: required supporting evidence is cited.
• Unsupported-claim rate.
• Abstention accuracy on no-answer and no-pack cases.
• Distractor and stale-source resistance.
• Answer coverage: fraction of eligible questions on which the system attempts an answer rather than abstaining; always report coverage beside accuracy to prevent over-abstention from looking successful.
• Time to first token, total latency, output tokens/s, peak memory, model/pack storage.
22.4 Mandatory ablations
22.5 Statistical/reporting rule
Report raw per-question results. For comparisons on the same questions, use paired bootstrap confidence intervals (or a paired permutation test when appropriate) on the per-question difference. Do not infer “no difference” merely because two separate confidence intervals overlap. Graph-Lite multi-hop results are exploratory because the multi-hop subset is small; report counts and effect sizes rather than a fine-grained activation claim.
23. Security threat model
23.1 Security invariants
• Transport is never trust: a pack may arrive by USB, SD card, share sheet, or untrusted storage; verification decides mountability.
• The model cannot install, remove, trust, or update packs.
• The pack cannot modify generator prompts or application policy.
• No generated answer is considered verified merely because its pack signature is valid.
• The UI distinguishes publisher verification, source provenance, and answer grounding as separate concepts.

Appendix B — Retrieval pseudocode
fun retrieve(query, activePacks, asOfDate): RetrievalResult {
    requireProductLanguage(query, "en")
    q = normalize(query)
    ids = extractIdentifiers(q)
    queryVec = embedder.encode(q)
    all = []

    for (pack in activePacks) {
        assert(pack.verified && pack.embeddingProfile == GRANITE_V1)
        eligibleSet = pack.eligibleRows(sourceAndChunkIntervals=true, asOfDate, queryJurisdiction)
        sparse = pack.fts.search(q, eligibleSet, k=24, ranksAreOneBased=true)
        dense  = pack.kdx.search(queryVec, eligibleSet, k=24, ranksAreOneBased=true)
        exact  = pack.aliases.resolve(ids).filter(eligibleSet).map(priorityTier=0)
        fused  = rrf(sparse, dense, k=60).map(priorityTier=1).take(16)
        candidates = exact + fused
        if (runtimeProfile == MOBILE_V1_GRAPH) {
            graph = pack.relations.oneHop(fused.take(6), limit=12)
                .filter(eligibleSet).map(priorityTier=2, rrfScore=null)
            candidates += graph
        }
        all += candidates.withPackProvenance(pack)
    }

    merged = deduplicateCanonical(all).takeBestDeterministically(32)
    if (!candidateRelevanceGateV1(merged)) return InsufficientEvidence
    tokenBudget = computeDynamicEvidenceBudgetWithMorTokenizer(query, merged)
    final = selectWithinBudgetCoverageAware(merged, maxChunks=4, maxTokens=tokenBudget)
    if (!finalEvidenceAdmissionGateV1(final)) return InsufficientEvidence
    return EvidenceSet(final.freeze())
}

Appendix G — Final one-page implementation contract
BUILD TIME (PC)
Authoritative sources → provenance → structure-aware chunks → canonical/search/generator text → aliases/relations → SQLite FTS5 → Granite-97M 384-d embeddings → KDX1 → 40-query development calibration → RFC8785 manifest → payload SHA-256 → Ed25519 → .kpack.

ANDROID INSTALL
Validate ZIP safety → verify raw manifest signature against bounded pinned trust-store keys → parse authenticated manifest and cross-check key_id → verify payload hashes → validate schema/KDX → run SQLite/FTS checks on a disposable writable copy → atomically install the untouched hash-verified DB read-only → Pack Registry.

ANDROID QUERY
English product question → user-selected verified packs → normalize query → source+chunk validity filters → BM25 top24 + exact dense top24 → local RRF(k=60) for ranking → identifier priority without auto-answer → CandidateRelevanceGateV1 → dynamic tokenizer-derived evidence budget (≤4 chunks, ≤1200 cap) → redundancy/coverage-aware final selection → FinalEvidenceAdmissionGateV1 → strict evidence prompt → GeneratorBackend → BUFFERED generation → citation/format validation → answer or insufficient evidence.

GENERATOR POLICY
Research primary: official 360M expert-choice MoR. Week-1 product continuity: SmolLM2-360M-Instruct must generate offline on the target phone through the standard fallback backend. MoR remains the Android target through Week 3; if research-only after the viability gate, desktop MoR research continues while the live product demo stays on the validated fallback.

SFT POLICY
G0 classifies PASS / PARTIAL / FAIL. Only PARTIAL triggers a 500–2,000-example pilot. Scale toward 5k/10k/20k only when a separate held-out gold-evidence set improves without grounding/abstention regressions.

CRITICAL PATH
KPack + hybrid retrieval + secure Android pack runtime + one validated Android generator + desktop MoR research. No full pretraining, no vector DB service, no neural query rewrite, no reranker, no KV packs, no router modification, no Wi-Fi Direct, no INT4 requirement.

CAPSTONE PROOF
No pack → no pack-derived evidence. Install signed Repair pack → grounded cited procedural answer. Install bounded law pack → English grounded answer + exact source + historical as-of behavior. Corrupt pack → reject. Remove pack → pack-derived evidence becomes unavailable. These demos do not claim erasure of information from model weights.
