# M4E3 diagnostics and lifecycle preparation

Prepared on 10 October 2026 while the repaired E2 full development suite runs. This is a source-bound dependency audit and acceptance plan, not E3 implementation or acceptance. E3 code must wait for complete E2 development/policy/restoration/parity/closure and a verified checkpoint. The owner supplies final knowledge content; signed synthetic tests remain permitted.

The frozen architecture requires a home latency-diagnostics toggle (paragraph 620), model hash/quantization, llama.cpp commit, reasoning/final token counts, embedder profile, retrieval candidates, timings and active versions (625). It requires one query at a time, replacement cancellation, the existing I/O/default executor boundaries, serialized generation, buffered raw output, reasoning removal and validation before display (627–631). The existing local-processing badge correctly describes the app's lack of network permission; mobile data remains on.

The current `MainActivity` shows captured query and freshness but no numeric diagnostic panel. `UiState` already owns the submitted query and completed `RuntimeTrace`. Read-only pack inspection preserves the same answer/trace/submission; new query, pack mutation and cancellation clear them through the existing epoch/join/mutex path. E2's safeDrawingPadding correction is now part of the current main viewport and must be retained. Do not replace this orchestration while adding presentation.

`RuntimeTrace` currently contains selected IDs, prefill/evidence/emitted counts, nullable reasoning and final-and-terminal partitions, nullable backend prefill/decode/first-emitted-token times, total and initialization times, selection decisions, frozen generation context and selected evidence. The full returned retrieval-candidate pool is not retained as a diagnostic DTO. `GenerationContext` owns copied query, pack identities, product limits, optional backend identity and authenticated manifest strings; it has no live registry reader. These captured values are suitable for completed-run diagnostics. Current active settings must never relabel an older trace.

`ProductSession.ask` starts its monotonic timer after construction of the ProductSession. On a cold query its initialization interval includes lazy Granite/generator creation; on a warm query that per-query initialization field is zero. It replaces the inner runtime's total with the session ask total. This total includes that query's lazy initialization and runtime, but excludes ViewModel queue waiting, ProductSession construction, previous registry creation and UI rendering. The inner runtime's original total is not separately retained. `GeneratorBackend.loadAndVerificationMs` exists and describes constructor hash verification plus load; it is not the time to the final visible answer. Capture any additional timing values with explicit scope instead of inferring them by subtracting unrelated fields.

The backend first-token field measures the first emitted model token, potentially hidden reasoning. It is not time to a visible answer. The runtime partitions emitted token IDs at the first actual closing-think token and otherwise leaves both partition counts unknown. The final-and-terminal count is not an exact count of visible final-answer text tokens. Early outcomes and cancellation must retain these distinctions; absent values must not be presented as zero. The UI must never show a raw generation buffer or rejected candidate text. No throughput value may be derived from absent, zero, nonfinite or differently scoped timings. Final throughput/thermal/resource acceptance remains M8.

The generator identity exposes actual constructor-verified model/template pins and a configured native-library pin. The native pin is currently checked against actual APK bytes during acceptance, not measured in process by the identity field. Label that distinction accurately. The quantization description belongs to the configured, hash-pinned artifact; do not pretend it was dynamically discovered from a running model. Captured signed embedder profile assertions and the configured verified profile must be distinguished from genuine calibration measurement. This product path does not use MoR, so do not invent optional MoR diagnostic values.

## Additional dispatcher audit before implementation

Read-only source inspection during E2 finds that `PackRagViewModel.ask` enters an outer `Dispatchers.IO` action, then runs all of `ProductSession.ask` on `Dispatchers.Default`. `Retrieval.retrieve` calls `ActivePack.sparse` synchronously, so the fixed SQLite FTS statement currently runs on that Default caller. The outer I/O action does not establish paragraph 628 compliance for this nested call. Lazy generator/embedder constructor file verification also occurs within the Default session call. Record this as a remaining software gap, not an accepted threading contract or a demonstrated performance bottleneck.

The registry currently holds its synchronized snapshot for the complete synchronous query. Any dispatcher repair must preserve that lifetime, active identity checks and cancellation/serialization. It must not suspend while holding a JVM monitor, dispatch a callback that tries to reacquire that same monitor from another thread, close readers during dense scoring, or weaken snapshot admission. `ActivePack.cosine` reads a mapped FloatBuffer and computes the score; it is CPU work distinct from the explicit SQLite statement. Choose the smallest architecture-consistent separation only after E2 closes, and fix independent thread/serialization assertions before changing runtime execution. Actual phone tests must verify the named I/O versus CPU boundaries in addition to unchanged ranks, token budgets, answers, cancellation and ownership. This preparation proposes no implementation and claims no compliance from thread names alone.

Navigation review also confirms that source and management screens use non-saveable `remember` state, with no `BackHandler`, and the current-law label is a separate sibling of the checkbox. Completed answer/submission survives Activity recreation through the ViewModel, but screen restoration, system Back behavior and merged accessible checkbox semantics need explicit E3 acceptance. Do not describe these behaviors as already verified by E1's captured-answer recreation test.

## Fixed lifecycle and diagnostic interpretation cases

These are independent expected invariants fixed before E3 code, not newly executed results or invented benchmark observations.

| Trigger | Required observable behavior |
|---|---|
| Invalid form input | Existing deterministic input error; no native initialization, no fabricated completed diagnostic trace. |
| Valid query with no active pack | NO_ACTIVE_PACK, no lazy model initialization or generated-token claim; captured empty pack selection remains attributable to that submission. |
| First actual query after a session opens | Initialization may be measured; total retains its explicitly bounded session-call scope. No claim of UI/queue time or visible-answer first-token timing. |
| Subsequent query in the same initialized session | Per-query initialization can be measured zero. That zero is distinct from an unavailable generator-load measurement or a missing timing. |
| Returned pool rejected before generation | Captured candidate/pack context may be shown if actually collected. No generated-token partition or backend decode measurement is manufactured. |
| Emitted tokens with no closing reasoning token | Both existing reasoning/remaining partition counts remain unknown; absence is not displayed as zero. No raw buffer is exposed. |
| Nullable or nonfinite timing; zero duration | Missing/invalid measurements are labelled; no finite throughput or visible-answer latency is inferred by division or subtraction. |
| Edit form controls after completion | Visible diagnostics and source links retain the completed submission's exact query/pack identity, rather than relabelling the old answer with the edited form. |
| Read-only active or inactive inspection | Exact answer/trace/submission remains owned and unchanged, including diagnostic candidate context; inspection cannot activate another version. |
| Submit a replacement while generation is active | Cancel the old pipeline and serialize the replacement. An old completion cannot attach answer/diagnostics/citation navigation to the replacement. |
| Cancel or mutate active content | Clear stale captured answer/diagnostic navigation according to the existing contract. Recovery query must still work through real native generation. |
| Activity recreation with a completed result | Preserve that result's captured diagnostic context. Citation/management navigation restoration, if supported, binds to the same existing result instead of saving live readers or serializing a raw buffer. |
| Process recreation without an in-memory result | Do not restore stale citation or diagnostic values as a new result, and do not automatically claim that previously active evidence has already been reverified. |
| System Back from citation/details/management | Return through the local screen hierarchy without accidentally exiting the app or mutating a registry; busy and confirmation behavior needs an explicit defined test. |
| Current-law checkbox accessed by its label | One labelled accessible checkbox control with the correct checked state; retained test tags and normal click behavior still work. |

Candidate diagnostics refer to the actual returned, capped/deduplicated/relevance-marked pool, not every row in a pack or a separately rerun retrieval. Show candidate IDs/hashes/ranks/scores and selection decisions with their captured pack/origin identities. A representative merged candidate's scores and relevance must not be silently attributed to every origin as an independently measured origin score. Profile/calibration data retains its authenticated-assertion label. These expectations must be connected to actual runtime snapshots and tests before E3 acceptance.

Diagnostic copying must not access `Candidate.generatorRendering` merely to describe a returned candidate: that property runs representation selection and can throw for unavailable/invalid English rendering. An irrelevant or ambiguous pool can legitimately return before prompt representation admission. Reusing FrozenEvidence for every diagnostic candidate would add a new early representation-selection path. Use only already returned immutable IDs/hashes/ranks/scores/relevance and copied origin assertions for the candidate display; selection/generator representation remains the existing admission path. Fix negative cases before implementing this capture so diagnostics cannot change an abstention into a representation exception.

The first implementation should be the smallest correct integrated diagnostic flow through the working app, then the adjacent lifecycle/accessibility and dispatcher controls. No performance optimization, native/compiler change, new retrieval architecture, owner final-pack creation, real licensing/review/calibration claim or final release-signing acceptance is authorized by this preparation. F follows complete E acceptance; M5/M6 software interfaces, M7 software evaluation and M8 release/physical/documentation/delivery retain their existing dependencies.
