## Installation and evidence discipline

The first separate visual attempt timed out in streamed product installation. A second attempt succeeded in both non-streaming installs but Android terminated its instrumentation with recorded PACKAGE UPDATED/installPackageLI. That attribution is based on actual process exit information; association with the earlier timed-out installer session is an inference. Those failed outputs remain preserved, including explicitly invalid cat-error captures and the second attempt's actual PREPARING marker with zero passing controls. The owner confirmed choosing Ne pas envoyer on the observed Play Protect dialog; the agent neither uploaded the APK nor changed security settings.

For these new builds, install_pair_serial.py reads the installed public APK hashes and replaces only mismatched APKs in place with serial non-streaming install-r commands. No uninstall/data clearing occurs. Every install must return Success and both actual installed hashes must match the selected pair before instrumentation. Three consecutive post-install hash checks are recorded; they do not promise protection against an unknown future installer. An installation timeout has unknown outcome and holds all tests/install retries until the pending decision/session is settled and identities are reverified. Each subsequent class uses the verified-installed runner: it checks both installed hashes again, without another reinstall.

run_adjacent_background.py runs one frozen class at a time, requires its exact JUnit method count, then saves all of its original report bytes through the existing collector before starting the next class. The driver validates original hashes, selected source hashes, compiled variant, fixed control counts, true control flags, explicit owner50 scope where reported, accepted74°C[S1] synthetic answers where reported, and canonical identity where present. Android sources are checked against the frozen build before/after every class. The test's frozen assertions also check the deeper runtime ownership, token and native behaviors described below. If any stage fails, no later class executes; failure-time reports are preserved as possibly stale/unaccepted, never promoted just because their JSON says PASS.
