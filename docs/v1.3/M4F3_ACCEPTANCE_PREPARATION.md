# M4F3 normative presentation acceptance — dependency preparation

Prepared read-only while the F2 approved-policy experiment runs. This is not F3 implementation or acceptance. Begin runtime changes only after full F2 closure/checkpoint. Requirements come from M4F_ASSET_READINESS_PREPARATION.md and the existing v1.3 normative screen audit; no new architecture or owner knowledge content is proposed.

The source audit confirms active packs currently appear as plain tags and installed rows omit publisher/freshness/size. Existing immutable PackDetails already owns authenticated publisher/key identity, update-check date and separate manifest/payload/transport byte counts. Installed-version trust labels alone cannot authenticate additional display metadata; inactive rows need verified inspection or a clearly unavailable status after inspection failure. Do not read unverified manifest filenames to populate authoritative rows, and do not conflate compressed transport bytes with payload/storage bytes.

Before implementation, freeze independent acceptance controls:

- Active pack chips expose the actual identity and navigable verified details; empty, one and multiple active packs render correctly. Versions sharing a pack ID must not alias tags or navigate to the wrong manifest identity.
- Installed publisher/key, version, verified trust, update-check date and separately labeled transport/payload bytes derive from authenticated owned values. A rejected/tampered inactive pack shows unavailable metadata and safe failure, never a stale verified claim. Reopening, activation/deactivation, deliberate older-version confirmation, rollback and removal refresh identity-bound values.
- Freshness remains advisory. Equality/before/after the signed date, device-clock comparison and captured submitted-query comparison are distinct; stale metadata alone must not reject otherwise valid evidence or alter the completed answer's context.
- Pack import shows actual observed copy/archive/signature/manifest/payload/database/index/commit events from the verifier and registry. No elapsed-time percentage or signature-passed label before successful verification. A stage failure preserves the preceding active pack and never displays accepted/unbuffered generation. Byte counters use explicitly stated byte domains; the import may have more than one copy/verification pass.
- Real rejection cases include signature, profile, archive, payload/hash, database/index and policy errors. Safe typed labels retain useful reason categories without private paths, raw reasoning or attacker-controlled markup. Existing consent and atomic registry assertions remain in force.
- Actions have accessible labels/roles, readable stage/status announcements and adequate touch targets. Scrollable long publishers/pack names, narrow portrait viewports, system bars, large font and screen recreation preserve primitive form/navigation state and completed owned answer/source/diagnostic attribution. Never persist native handles, mutable external URIs or raw reasoning.
- Host format/presentation contracts, adjacent registry/ViewModel integration and existing regressions pass. Physical foreground controls and independent exact-PNG review must show visible required fields. Every runtime-touching iteration retains actual signed synthetic question → verified active pack → retrieval/admission/selection → pinned LFM2.5 → reasoning removal/citation validation → accepted answer or deterministic abstention.

On failure, preserve originals and hold F4. On success, save selected source/APK/input manifests, original results/PNGs, policy parity, restored development consent and explicit public-file custody before immutable F3 closure. Real licensing/calibration, final owner packs, controlled performance and the final nondebug signed release are not inferred from these presentation tests.
