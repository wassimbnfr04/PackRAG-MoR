# D3 dependency audit and acceptance preparation

Recorded 9 October 2026 while D2's full physical gate runs. This is read-only design preparation, not D3 implementation or acceptance. D3 must wait for complete D2 development/policy/restoration/closure and a verified checkpoint. Architecture paragraphs519/521/532/536/546/548/998, M4D_EVIDENCE_PREPARATION.md and the existing conflict ADR govern the work. No model/constants/profile/native optimization or benchmark gold is introduced by this audit.

## Present working path and gaps

D1 already supplies an ordered, eligible, deduplicated, globally capped candidate pool and representative retrieval relevance. C2b supplies conflict decisions and required canonical hash pairs without graph injection. D2 resolves an immutable generator rendering once per candidate and budgets/serializes the actual rendering. Both prompts greedily try candidates in their current order, stop at four selected chunks, and count complete-template/evidence tokens. A final selected relevance/eligibility/conflict check is present. The real walking/conflict/relevance/representation paths pass the current desktop and completed new phone-method checks; the complete D2 gate is still pending.

The greedy trial is not yet an atomic conflict-bundle selector. A required companion can be omitted by budget/chunk caps and rejected only after selection. The correct current rejection remains immutable evidence; D3 should choose complete bundles deterministically where they fit and reject missing/oversized required bundles safely. It must never retrieve a companion from outside the eligible candidate pool or invent a score.

Literal duplicate source/text pairs are already merged during retrieval with origin preservation. More general redundancy has not been implemented. Shared words or one text containing another do not establish equivalent legal propositions: negation, conditions, exceptions and version differences may change the meaning. D3 needs an explicit conservative rule with independently fixed positive/negative examples and a record of every dropped candidate. It must preserve distinct facts/source coverage and mandatory companion evidence.

Python Candidate is a frozen wrapper around mutable chunk dictionaries and a live VerifiedPack. PreparedPrompt owns generator rendering DTOs but retains these live candidate references. Python runtime subsequently builds citation records from candidate dictionaries. Its identity check is immediately before generation; SessionRegistry snapshots are sorted but its public active map is mutable. Android Chunk and GeneratorRepresentation have immutable scalar values and registry.withSnapshot holds the monitor throughout the runtime call. However, PreparedPrompt still exposes candidate/pack references and IntArray/List objects. A read-only interface or val does not itself guarantee defensive ownership of all nested arrays/collections. Both platforms need a frozen evidence value separate from live reader state and clearly bounded mutation/version checks.

## Candidate implementation choices to settle after D2

Additional source-bound clarification from paragraphs536/521 and546 (read-only preparation while repaired D2 runs): canonical duplicate detection remains the required original-source hash plus canonical-text hash. Do not silently replace that frozen identity with a wider context key or a semantic similarity rule. Preserve each merged origin's pack/version/manifest and source/chunk/context metadata rather than treating the representative's metadata as every origin's metadata. Selection-level redundancy may safely remove repeated identical evidence values only when their complete source/version/validity/status/rendering/relationship context agrees; differing contexts or nonidentical propositions remain explicit. Where an optional coverage preference is introduced, specify its exact ordering and fixed expected decisions before coding. It must preserve candidate scores/ranks, mandatory conflict members and final selected relevance. A source-coverage statistic is a recorded count, not proof of sufficiency. These are constraints for the later D3 implementation, not acceptance or a new runtime change.

Use the existing retrieval order as the deterministic base; do not add an authority-wide sort or second RRF. A conflict bundle's members come only from retrieved eligible required canonical pairs. Expand the selected trial atomically, deduplicate shared members, and present the resulting evidence in original candidate order. Use actual complete-template/evidence costs for each trial; do not sum per-chunk token estimates because IDs/envelopes/template boundaries affect costs. Oversized/missing mandatory evidence must be explicitly recorded/rejected, never silently truncated.

Prefer conservative literal-duplicate handling with strict source/version/jurisdiction/validity/status/representation context rather than semantic similarity. Mandatory conflict members are exempt from ordinary redundancy elimination. Any allowed representative must retain all discarded origin identities and the reason, including canonical and rendering hashes. A same-text different original document is not automatically the same legal interpretation; unknown/different versions, status, authority, validity, jurisdiction or relation metadata must prevent unsafe merging. Nonidentical facts remain candidates in base order; no language-model reranker, overlap threshold or held-out tuning is justified here. Exact policy and independent expected cases must be recorded in DECISIONS before implementation; architecture changes would require an ADR.

A frozen evidence record should own the fields required by546: evidence ID, pack/version/manifest identity and every origin, chunk/source ID, title/locator, exact canonical text/language/hash and original source hash, actual rendering/provenance/hash, jurisdiction, original/effective validity and legal status, original ranks/scores/global position, identifier/relevance and conflict/relationship metadata. Freeze raw/normalized query/as-of/current-law/jurisdiction, sorted active identities, mobile-v1 profile/caps, pinned product model/template/runtime identities and exact prompt tokens/budgets. Token arrays and nested collections need defensive copies; citations and diagnostics should use the frozen values. Admission must check actual selected relevance, validity, required companions and pack consistency rather than discarded candidate flags.

## Independently verifiable acceptance order

1. Fix pure expected selection plans before invoking the selector. Cases include empty/no-relevant pools, reversed caller/pack input, repeated candidate/origin, known literal duplication versus different version/context, distinct overlapping facts, new source coverage, shared/multiple conflict bundles and missing required members. Scores and ranks must remain unchanged; no synthetic companion appears.
2. Test actual four/evidence1200/prefill1536/context2048/generated512 constraints, inclusive boundaries and ordinary XML quoting. Unit cost oracles verify selection control flow only; actual GGUF/template token cases establish the real budget. Oversized relevant evidence versus smaller irrelevant evidence must fail final admission; skipped candidates must have explicit reasons. A budget failure must not corrupt a previous complete trial or partially admit a required bundle.
3. Test ownership and identity: mutate caller lists/dictionaries/arrays and reader-derived metadata after preparation; frozen prompt/citation/provenance bytes must stay unchanged. Change active pack/version/as-of/profile at the declared admission boundary and reject inconsistent state. Preserve sorted identities and every deduplicated origin. Record exact scope: a simulated mutation is not physical filesystem race or power-loss proof.
4. Generate fresh signed adjacent fixtures against actual canonical Granite inputs with independent retained-set/state/companion expectations. Retain all old signed corpora and numeric references; any intentional changed selection gets a new versioned reference with an explanation and unchanged original source hashes. No rewrite of historical experiments or fitted gold.
5. Pass relevant pure/format/interface/adjacent and complete existing Python/host regressions. Then rerun all four actual desktop flows plus the new selection/freeze/budget cases and exact full-template tokens. Debug/demo inputs must match; model/template/JNI remain pinned.
6. Execute new physical selector/tokenizer/runtime methods plus all retained development and compiled-policy methods. Save every final JSON/original ADB byte before switching variants. Compare exact tokens/admissions/frozen provenance/selected supported budgets across platforms, restore owner development/consent, and close source/history/output hashes before E progression.

These cases establish correctness/integration and explicit rejection behavior, not real legal review, semantic sufficiency, measured calibration, held-out accuracy, peak memory, performance, final signing or complete product acceptance. Those remain E/F and M5-M8.
